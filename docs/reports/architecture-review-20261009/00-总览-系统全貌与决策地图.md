# 00 · 总览：系统全貌与决策地图

## 1. 产品侧：这套系统是什么

一句话：**给包装（及电池/其它行业）做「从需求到报价、再到技术工艺落地」的一条线上流水线**，把过去靠工程师电脑里的 Excel、BOM、工艺文件口头传递的环节，搬进一个有留痕、有门禁、有权限的系统。

产品上分四块能力：

1. **报价工作台（正向报价）**：销售录入需求（文字/Excel/PDF/图片/图纸）→ 系统推荐产品与参数 → 6 步走完得到正式报价 → 导出 Word / 写入业务库。
2. **快速报价（逆向报价）**：没有完整工艺数据时的通用做法 —— 从**标准报价案例库**里找相似案例，销售挑一个基准，只改差异参数，直接出差异价。**全程不进入技术工艺链路**。
3. **技术工艺工作台**：工程师侧，把报价交接包变成可落地的零件清单、BOM、工艺路线、成本，再回传给报价形成产品行。
4. **包装图纸解析**：DWG 上传 → 转 DXF → CAD IR → 语义层 → 业务部件（零件）→ 供 BOM/工艺/成本消费。

行业是可扩展的一等概念：`packaging`（包装）是目前做得最深的行业；`battery`（电池）等走既有的整机口径。

## 2. 技术侧：运行时拓扑

一套代码，两种进程形态，三个端口：

```
浏览器
  │
  ├─ :8010  cpq_suite_server.py（ThreadingHTTPServer，单文件 1131 行）
  │     ├─ 静态文件：仓库根目录下的 *.html / *.js / *.css（报价首页.html 是入口）
  │     ├─ /agents/quote|config|rule  → 三个助手（报价/配置/规则），先验票再干活
  │     ├─ /auth/*                    → 登录、账号、密码
  │     ├─ /product-image/<成品编码>   → 同源取图，复用 8011 的目录
  │     ├─ /api/*  /apps/*            → 反向代理到 :8012（技术工艺）
  │     └─ 命不中的路径              → 也代理到 :8012（技术工艺前端页面）
  │
  ├─ :8011  产品图片服务（与 8010 同进程、后台线程）
  │
  └─ :8012  tech_app_launch.py → uvicorn backend.main:app（FastAPI，子进程）
        ├─ 技术工艺全部 REST API（backend/main.py）
        ├─ /api/projects/{pid}/drawing-flow/run  ← 包装图纸八步链路入口
        └─ 技术工艺前端（tech_app/frontend/*.js）
```

关键点：

- **8012 是 8010 的子进程**（`cpq_suite_server.py:1007` `subprocess.Popen`）。所以部署时必须**先停子、再停父**，重启由父进程重新拉起子进程；启动命令里必须带 `PATH` 前缀（见 §4）。
- 8010 自己是**单文件** HTTP 服务，没有框架。路由靠 `do_GET/do_POST/do_PUT` + 一串 `_dispatch_*` 手写分派。
- 报价侧和技术工艺侧**共用一套模型网关与设置**（`cpq_settings.json` 不对外暴露，见 `_BLOCKED_FILES`）。

## 3. 数据面：两套存储

| 存储 | 位置 | 存什么 | 特点 |
| --- | --- | --- | --- |
| **文档位（项目数据）** | `tech_app/tech_data/<project_id>/` | 需求、CAD IR、零件、BOM、工艺、成本、快照、版本 | 一个项目一个目录；每个文档自己版本化（`meta_backend.get_doc/put_doc` + `MAX_VERSIONS`） |
| **PG 知识库** | `cpq_kb` 库，32 张表（含 9 张 `kb_packaging_*` + 3 张 `kb_quick_quote_*`） | 案例库、费率、规则、DA 本体、工艺路线 | 有 `kb_meta` / `kb_version`；写入前有预检（`empty_required_table` / `demo_only`） |

文档位的设计意图：**解析产物是「文件」不是「行」**，一次解析可以整份落盘、留哈希、留版本，回滚只需切版本。代价是没有跨项目的查询能力——这就是后来要建 PG 知识库的原因。

## 4. 全局决策地图（最关键的 10 条）

| # | 决策 | 原因 | 代价 / 后遗症 |
| --- | --- | --- | --- |
| 1 | 技术工艺做成**独立 FastAPI 应用**，由报价服务当子进程拉起并反向代理 | 复用既有 `process_drawing` 全链路代码，不动报价侧 | 引入父子进程生命周期耦合；部署顺序、PATH 极易踩坑（34 曾因此静默回退 LibreDWG） |
| 2 | 8010 **不用框架**，手写路由 | 历史包袱最小、起步快 | 路由与鉴权分散，靠测试冻结（计数断言）来防漏；可读性一般 |
| 3 | 报价侧把**正式报价的最后一公里**（导出 Word / 写业务库）做成服务端门禁 | 前端按钮禁用不算门禁，绕过接口就失效 | 门禁逻辑集中在 `cpq_agent_server.py`，后来抽出 `cpq_quote_gate.py` 共用 |
| 4 | 图纸解析采用**「确定性优先 + 模型只判语义」**分层 | 模型会编尺寸、编件名；报价不能有幻觉 | 需要大量规则与人工确认环节，链路长 |
| 5 | **不读 BOM、不读金标**作为解析输入 | 金标是「对答案」用的，喂进去等于泄题 | 真实正确率无法用单测证明，只能另做实图抽检 |
| 6 | 模型只能**从已有候选里选、只能说语义**，不能产出 CAD ID / 尺寸 | 同上，防幻觉 | 模型不可用时要有确定性降级路径（`model_failure_isolation` 门禁项） |
| 7 | 零件**几何连通分量 ≠ 业务件**，中间加一层「业务部件」 | 一张图 263 个几何分量，业务上只有二十几件 | 多一层映射与人工确认；件数口径要反复对账 |
| 8 | 一切未确认的数据**不许进正式成本/正式报价**，允许「带缺口草稿」先行 | 演示与内部预览要能走通，但不能骗客户 | 出现 `draft_only` / `has_gaps` 这类状态面，前端要如实披露 |
| 9 | 工作方式固定为 **Spec → 红测（先跑失败）→ 提示词交给 DeepSeek 实现 → Codex 验收** | 让「什么算做完」可机械判定，避免口头验收 | 流程重；旧冻结断言变更必须显式「精确重指」，不能放宽 |
| 10 | 部署只有一个**唯一可执行版本**：`scripts/deploy_34_bare.sh` | 手工部署漏配置会造成静默降级 | 脚本 720 行，本身就是需要维护的资产 |

## 5. 能力边界（不能越线的话术）

- **DWG 编排能力完成，真实转换能力未验收**——这句话是三条文档（`DEPLOYMENT.md`、门禁脚本 `_CLAIM_LINE`、changelog）一致的硬口径。
- **19 项**上线门禁里 `converter_license`（转换器许可与部署方式已由业务/法务确认）与 `real_samples_e2e_passed`（两份真实样本 L4 通过且金标已人工审批）是**人工项**，Agent 不得代签；其余 17 项为自动项。（门禁清单源码注释仍写「18 项」，是陈旧注释，以 `GATE_ITEMS` 实际条数为准。）
- 「八步链路 8/8 completed」只代表**编排跑完**，不代表零件正确、尺寸正确或报价可交付。
- 事实标注：`[本地已实现]` = 代码在本地 HEAD 已具备；`[已上线待验收]` = 已部署 34 但未按业务口径验收；`[仍缺实现]` = 本地与线上都没有（定义见 `README.md`）。
- 真实实图验收的已知水位（10-8 记录）：酒盒 28 条业务件中 26 条有几何尺寸、**仅 9 条**有管线确认的尺寸证据；圆盘盒（未拆方案）55 条中 36 条有尺寸、**仅 3 条**有确认证据。这是「最需要人盯着」的地方。
