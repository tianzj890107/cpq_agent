# 02 · 快速报价（逆向报价）

## 1. 产品侧

### 1.1 为什么会有这条路

正向报价要求「工艺数据齐全」——要先有零件、BOM、工艺路线，才能算出准价。但现实里销售面对的常常是「客户给了个需求/一张图，问大概多少钱」。这时候正确的做法不是硬算，而是：**找一个历史上真实成交过的相似案例，按差异项加减钱。**

所以首页把报价拆成两个入口（`报价首页.html:1291`，两者都只对包装行业可见）：

- **精准报价**：走既有 6 步链路。
- **快速报价**：从标准成交案例出发。

### 1.2 全流程

```
输入需求 / 上传文件
  → 识别包装关键参数（盒型、结构、尺寸、材料、工艺、数量）
  → 查询标准报价案例库
  → 返回 3~5 个相似案例（带相似度、标准报价、报价日期、相同项、差异项、来源、是否已审核、为什么排这个位置）
  → 销售人工选择基准案例        ← 模型不替用户决定
  → 在右侧字段工作区修改少量差异参数
  → 计算差异价格
  → 生成快速报价
```

### 1.3 一版明确**不做**的事（复杂度控制）

- 不自动关联工程师电脑里的历史 BOM / 工艺文件。
- 不生成新的技术工艺。
- 不重建完整 BOM。
- 不做精准成本核算。
- 不走技术工艺审批、不做报告发布回传。

**快速报价全程停留在报价工作台**，不进技术工艺。

### 1.4 交互设计：Agent 是入口，工作区是权威

- **左侧 Agent**：理解需求、解释候选、接受自然语言修改（「把数量改成 3000，面纸改成 250g，再增加烫金」）。
- **右侧工作区**：结构化展示与编辑，四列对比表「参数 / 基准案例 / 当前报价 / 差异价格」。

原因（很重要，这解释了为什么不是纯对话）：

- 尺寸、数量、材料必须一眼可见；
- 用户要能对比原案例值与新报价值；
- 避免 Agent 误解「改成 250」到底是克重、数量还是尺寸；
- 保存与审计更可靠，能下拉、能单位/范围校验；
- 每次都明确展示「这一项改了多少价」。

**Agent 只把修改建议写进工作区，用户确认后才落库。**

### 1.5 适用门槛与风险提示

命中已审核案例、盒型兼容、没有未知特殊工艺、尺寸差异不超阈值、数量在支持区间、案例价格没过期 —— 全部满足才算「快速报价适用」。超范围时**不硬算**，提示：

> 当前需求与标准案例差异较大，快速报价可能失真，建议转精准报价。

并提供**一键转精准报价**：把已填数据带进技术工艺，不重新输入。

### 2.2 存储

| 表 | 位置 | 作用 |
| --- | --- | --- |
| `cpq_qq_standard_case` | 报价侧 schema | 标准报价案例（`CASE_TABLE`） |
| `kb_quick_quote_config` | `cpq_kb` | 有效期口径等配置 |
| `kb_quick_quote_match_weight` | `cpq_kb` | 匹配权重 |

设计要点：**案例落在报价侧 schema，费率/权重落在知识库侧**。前者是业务数据，后者是「口径」，要按知识库的审核与版本规则走（`rule_authority` / `authority_summary` 会告警「演示数据」）。

### 2.3 关键决策与原因

| 决策 | 原因 |
| --- | --- |
| 匹配**两阶段**：先盒型/结构硬筛选，再按尺寸/材料/工艺/数量算相似度 | 硬筛选保证不会把「天地盖」匹配到「圆盘盒」；软打分负责排序 |
| 返回 **3~5 个候选**并逐项解释 | 让销售判断，而不是让模型替销售背锅 |
| 差异价是**基准价 + 各项修正**，不是重算 | 重算需要完整 BOM/工艺，那就成了精准报价 |
| 差异规则带**来源与审核状态**，演示数据要显式告警 | 报价要给客户，不能拿 demo 费率当权威 |
| 文件解析**调统一服务**而不是自带解析器 | 报价与技术工艺共享同一套 DWG 解析能力，不装第二套 ODA |
| 快速报价**不写技术工艺** | 复杂度控制，也避免污染工艺链路 |
