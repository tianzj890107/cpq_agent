# 04 · 技术工艺骨架：阶段、任务、权限与工作台

## 1. 产品侧

### 1.1 五阶段 × 十三子步骤

技术工艺不是「一个页面」，而是一张**编号表**（`tech_app/backend/services/workflow_stages.py:12`）：

| 阶段 | 标题 | 子步骤 |
| --- | --- | --- |
| 1 | 工艺评估需求 | 1.1 创建需求 · 1.2 确认需求 · 1.3 审核需求 |
| 2 | 图纸解析 | 2.1 图纸解析 |
| 3 | 组装与整合 | 3.1 整合图纸 · 3.2 参数推荐 · 3.3 组装工艺 |
| 4 | 成本测算 | 4.1 零件成本 · 4.2 组装成本 · 4.3 汇总 |
| 5 | 工艺评估报告 | 5.1 汇总结果 · 5.2 结果审核 · 5.3 发布并回传报价 |

**这张表的行序 = 依赖顺序，不是阶段号顺序**。原因写在代码注释里（`workflow_stages.py:26`）：图纸解析第 8 步 `field_write` 要把图纸读出的字段回写进需求单，所以它必须排在「1.1 创建需求」之后、「1.2 确认需求」之前 —— 因为 1.1 提交/1.2 通过/1.3 审核都会把需求推离可编辑状态，先确认再解析必然 `REQUIREMENT_NOT_EDITABLE`（实测 7/8 会踩）。用户顺着流程栏点下去就该是对的，所以表就按「创建需求 → 图纸解析 → 确认需求 → 审核需求 → …」排。

包装行业在第三阶段把页签改成 **3.1 方案与部件 / 3.2 排版排模 / 3.3 后道加工与组装工艺**（仅包装生效，stage id 与 view key 不变，其它行业不受影响）。

### 1.2 角色与可见范围

10 个角色（`tech_app/backend/services/auth.py:29`）：只读用户、工艺工程师、销售经理、工艺经理、校核员、工艺技术总监、销售总监、财务经理、总经理、管理员。

几组关键角色集（
`WRITE_ROLES` 建模/改参、`MANAGER_ROLES` 需求与评估报告主责、`REVIEW_ROLES` 通用校核、`DIRECTOR_ROLES` 终审、`FINANCE_ROLES` / `COST_ROLES` 成本、`SALES_MANAGER_ROLES` 销售主数据）。

**「为什么我只看到两个项目」是一个产品设计，不是数据丢了**：可见范围按角色算（`project_access.can_read()` / `visible_projects()`），不是全公司可见。归档项目对非 owner 一律不可见；销售能看到的多半是「自己有报价 / 报价关联 / 成本财务交接」的项目。所以同一批数据里 `PE1`（工艺经理）看到 33 个、`FI1`（财务）15 个、`SM1`（销售）可能只有 2 个。

### 1.3 任务卡与支线

技术工艺侧收到的不是「工单」而是**带来源的卡片**（来源有报价、成本任务、独立新建），任务类型决定它是否推进报价步骤：

- 常规 handoff：做完推进下一步；
- 支线（`tech_new_product` / `tech_cost`）：做完只回结果，**报价卡片留在原步骤等**。

### 1.4 草稿与正式的分界

`workflow_projection` 给包装草稿的分析步骤打 `draft_only = true`：「图纸都还没正式确认，但可以让销售先看到解析结果和成本试算」。这**不等于**放行审批 —— 送审/发布接口有各自的门禁，草稿可用性只是让步骤「可点」。

### 2.1 渐进加载（`## 533`，10-9 上线）

这是最近一次「体感」优化，值得单独记：

- **项目列表**：`/api/projects?page=&page_size=6&q=` 只返回权限筛选后**当前页的元数据**，不再为卡片展示调用 `build_card`、不读 IR/BOM/成本/会话明细。旧的无分页参数接口保持兼容。
- 实测收益（34，PE1）：旧口径 `visible_projects(mine)` 42 条 **16.93 秒** → 新口径 `visible_projects_page(mine, 1, 6)` 6/42 条 **0.003 秒**。
- **工艺工作台**：卡片先跳工作台，再按需恢复该项目阶段；第 2 步已存零件和主体先显示，流程/角色映射/BOM 补算不挡页面就绪；有跨项目迟到结果保护。

### 2.2 关键决策与原因

| 决策 | 原因 |
| --- | --- |
| 编号表**只描述编号与标题**，stage id / URL / iframe 参数 / 消息协议一律不变 | 历史链接、历史会话、历史任务不受影响 |
| 编号表独立成模块 | 编号要在后端提示词、前端阶段表、各页页签、流程条四处说同一句话，写死多处必然漂移（曾出现「顶部第 3 阶段、页内 2.2」） |
| 列表接口与卡片详情**彻底分离** | 16.93 秒的根因是「为了画列表把所有详情都读了」 |
| 草稿可用但审批不放行 | 演示与内部评审要能走通，正式门禁不能被绕 |
| 可见范围按角色算 | 工艺数据敏感；同时避免销售被无关项目淹没 |

## 3. 已知缺口

- 角色可见范围**没有面向用户的解释页**：「为什么只有 2 个项目」需要有人现场解释，属于可用性缺口。
- `workflow_projection` 里为草稿放的几条「跳过前置步骤」是有条件的补丁式判断（按 `key` 与 `prior` 白名单），**新增阶段时要同步改这里**，容易漏。
- 前端阶段表与后端 `workflow_stages.py` 靠人工保持一致，没有自动比对（只有测试冻结）。
