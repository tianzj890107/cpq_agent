# 06 · 包装语义层与业务部件提取（为什么「零件」最容易出问题）

## 1. 产品侧

### 1.1 三个层次，别混

| 层次 | 是什么 | 数量级（酒盒） |
| --- | --- | --- |
| **图元** | DWG 里的线、弧、标注、文字 | 6569 个实体 |
| **几何区域 / 几何零件** | 按图元做连通分量得到的封闭块 | 263 件 |
| **业务部件（业务件）** | 工程师口里的「左盖面纸、内托、磁铁」 | 28 件（待确认） |

**263 ≠ 28。** 系统里「零件」这个词同时被这三个层次用过，这是历史上最容易产生误解的地方。当前口径已经统一：**业务件是成本、工艺、报告清单的唯一计件对象；几何区域只是证据。**

### 1.2 为什么「业务件」这么难

因为图纸里没有「这是一件」的标记。工程师靠经验：看块名、看材料标注、看图层、看排版位置。系统要复现这件事，必须把多种线索合起来判断：

- 名称锚点（如 `左盖面纸`）、材料标注（`225G铜版底PET光银`）、尺寸标注；
- 块路径、图层角色；
- 排版空间证据（同一排模里的重复副本不能各算一件）。

### 1.3 现在的交互水位

- 右栏给出「业务部件」清单（默认来自图纸推导，标「待人工确认」）；
- 每件最多 8 个 CAD 图形候选，按可复算的证据分排序，**未确认候选封顶 85%**，页面明确写「这不是统计正确率」；
- 最高分且图元完整、不与别件冲突的候选**自动归属**（`bound_by=auto`），但**尺寸仍需人工确认**；
- 多片段件：每片的 CAD ID、图层、矩形、是否已确认都保留，同件只计一次；
- 已有人工绑定不会被自动覆盖；改选不同图元会清掉旧确认尺寸并留历史。

## 2. 技术侧

### 2.1 语义层（`services/packaging_semantics/`）

| 文件 | 职责 |
| --- | --- |
| `model.py` | 版本常量 `SEMANTICS_VERSION = "packaging-semantics/1"`、字段白名单、必需键 |
| `rules.py` | 图层规则加载与校验。`match` 键是**闭集** `{names, name_prefix, name_contains}`，闭集外的键抛 `LayerRulesError`（对外码 `PACKAGING_LAYER_RULES_INVALID`），**不许静默丢弃** |
| `roles.py` | `_match_rule()`：大小写不敏感、去首尾空白的包含匹配 |
| `geometry_semantics.py` | 轮廓/几何语义：闭合判定、图框识别、sheet extent、重复组 |
| `fields.py` | 成品尺寸字段、盒型候选 |
| `model_assist.py` | 模型只做语义判断（选候选、判文字） |
| `persistence.py` | 版本化落盘（`get_doc/put_doc` + `MAX_VERSIONS`），是后续模块的范式 |
| `provenance.py` | 证据与来源 |

图层规则文件：`tech_app/agent_knowledge/rules/packaging_layer_rules.json`，`rule_set=packaging_layer_rules_v1`、`review_status=reviewed`。

### 2.2 成品轮廓的三层判定

1. **产品级闭合候选**：`is_closed` 且**不属于** frame 图层角色、不是 sheet extent（bbox 与图纸 extents 任一方向差 ≤1%）、不是 panel repeat（落在 `repeated_groups` 里 count ≥ 2 的组）。取面积最大者。
2. **产品级圆**：`kind=circle` 且直径 ≥ 100mm，取最大，写 `inner_length/inner_width`，标 `origin=inferred_from_geometry`、`status=needs_confirmation`、`confidence ≤ 0.8`。
3. **都没有** → 尺寸必须 `missing` + `unresolved`，原因 `product_outline_uncertain`。

被排除的候选不删，逐条进 `outline.rejected[]`（含 reason / bbox / area / 证据引用，按 `(reason, -area, outline_id)` 排序）——**「为什么不是这件」必须可回答**。

### 2.3 几何零件提取（`services/packaging_parts.py`）

- `ENGINE_VERSION = "packaging-parts/1"`；零件 = `geometry.components`（连通分量）。
- 过滤参数 `DEFAULT_OPTIONS = {min_area_mm2: 2000, max_edge_mm: 1200, max_area_mm2: 1000000, max_parts: 64}`；被过滤的逐件记 `reason`（`edge_over_max` / `area_over_max` / `area_under_min` / `no_curve_entity`）。
- 排序 `(area_mm2 desc, component_id asc)`；重复件标 `repeat_of` 不删；超上限截断并给 `stats.truncated`。
- **单位未确认不写数值**；不可用时 `parts=[]` 且 `unavailable` 必须给出 `no_components` / `all_filtered` / `no_unit`。
- 零件编码 `DWG-P%02d`。

### 2.4 业务部件解析（`services/packaging_business_part_resolver.py`）

输入**只有 DWG**（附件/知识库一律不传），所以 `authority_source` 只有 `dwg` / `missing` 两种。

- 文字锚点排除原因闭集：视图标题 / 产地备注 / 方案名 / 标题栏栏位 / 材料表头 / 整盒自称 / `layout_instruction`（排模说明）/ `layout_zone_label`（右半区排版标签）/ `section_heading`（如「外盒」）。
- `strict_schemes`：图纸含**多个互斥方案**时直接抛 `multiple_packaging_schemes`，不合成混合 BOM（一键解析回 409，流程步记 unavailable）。
- 推导行的 `declared_sections`（复合名称的组成声明）、`name_from_drawing`、事实档（`observed` / `inferred` / 待确认）。

### 2.5 自动归属

- 候选分由**服务端**从候选本身重算（不信任浏览器传来的分数/实体列表）；同分按候选 ID/原序稳定决胜。
- 排序分上限 **0.85**（后端 `packaging_parts.py:4596`、前端 `app.js:3982` 同一口径）——「未确认」永远拿不到满分。
- 自动绑定条件：最高分、图元完整、未被别件占用；写出 `bound_by=auto`、`attribution.status=auto_selected`，**不伪造** `human_confirmed` / 操作者 / `size_confirmed`。
- 重复运行不产生新版本、不重复审计。

### 2.6 关键决策与原因

| 决策 | 原因 |
| --- | --- |
| 几何分量**不等于**业务件，中间必有映射层 | 263 个分量直接当零件计价是错的 |
| 规则闭集外**抛错而不是忽略** | 静默丢弃会让「规则改了但没生效」无从察觉 |
| 被排除的候选**留痕**（`rejected[]`） | 用户问「为什么不是这件」要答得出来 |
| 名称/材料/标注/块路径/图层/排版**多证据合并** | 单一证据都不可靠（重名、镜像、复制粘贴） |
| 自动归属**不越等**成尺寸确认 | 归属对 ≠ 尺寸对；尺寸错直接导致成本错 |
| 「不要把估算写成确认」——包围盒估算不放行正式单件工艺/成本 | 唯一能防「看起来完整其实全错」的护栏 |
| 多方案图纸**拒绝解析**而不是猜一个 | 圆盘盒上/下是两个互斥方案，混在一起必然算错 |

## 3. 已知缺口（这是全系统最大的风险区）

1. **尺寸证据覆盖率低**（10-8 实图只读诊断）：酒盒 28 件中 26 件有几何尺寸、**仅 9 件**有管线确认的尺寸证据；圆盘盒（未拆方案）55 件中 36 件有尺寸、**仅 3 件**有确认证据。剩下靠人工确认。
2. **业务件正确率没有独立评价集**：两份样本既是开发样本又是验收样本，等于没有留出图。
3. 同名/镜像/复制件的「同件判定」依赖规则，**极端排版下仍可能多算或漏算**（Spec 自己写了「多组成件与真实图纸仍需逐件复验」）。
4. 圆盘盒的多方案必须**先拆图**才能解析，这一步目前在离线工具里（`split_round_box_schemes.py`），切割坐标只适用该样图。

## 4. 可优化项（供拍板）

### 产品侧

| 优化 | 收益 | 代价 | 风险 | 我的建议 |
| --- | --- | --- | --- | --- |
| 把「几何区域 / 几何零件 / 业务件」三个词在页面上彻底分开命名并给出数量对照 | 直接消除 263 vs 28 的困惑 | 小 | 低 | **建议做（优先级最高）** |
| 业务件列表默认按「有确认尺寸 / 待确认」分组 | 工程师先干能干的 | 中 | 低 | 建议做 |
| 提供「一键带出所有待确认件」的批量确认界面（而不是逐件点） | 28 件的确认工时可接受 | 中 | 中（批量确认要防手滑） | 建议做，但要有二次确认与可撤销 |
| 明确「哪些图不建议自动识别，直接人工建档」 | 避免在不适合的图上浪费工时 | 低 | 低 | 建议做 |

### 技术侧

| 优化 | 收益 | 代价 | 风险 | 我的建议 |
| --- | --- | --- | --- | --- |
| **建立留出图（hold-out）评价集**：至少 5~10 张不参与开发的真实图，人工标注业务件与尺寸，作为正确率指标 | 唯一能让「正确率」变成可决策数字 | 人工标注成本高 | 低 | **建议做（战略级）** |
| 把「证据分」的权重与特征显式配置化并记录版本 | 调整可复现、可回滚 | 中 | 低 | 建议做 |
| 引入**尺寸标注的强校验**（径向/线性标注必须匹配真实图元 + 见证点）的覆盖率统计 | 把「9/28」这个数字做成日报 | 小 | 低 | 建议做，规格里已有判据 |
| 多片段件的组成归属给出「拆/不拆」两套候选让工程师选 | 复杂件的判断交给人 | 中 | 低 | 建议做，作为无法自动化时的兜底 |
