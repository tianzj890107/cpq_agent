# 11 · 全流程逻辑（端到端）

> 本文只讲**流程怎么走、每步的输入与产出、以及为什么这么走**；不列优化项、不列缺口清单（那些在
> `10-待拍板优化清单.md` 与各章 §3/§4）。事实口径与同目录其它文档一致：
> `[本地已实现]` / `[已上线待验收]` / `[仍缺实现]`。本文是只读分析产物，不改任何代码与数据。

## 0. 一句话

系统有**三条主链路 + 两条支线**，它们靠两个「交接包」串起来：

```
链路 A 正向报价（精准）        链路 B 快速报价（逆向）
  需求 → 推荐 → 6 步 → 导出       文件 → 相似案例 → 人工选基准 → 差异价
        │                                        （全程不进技术工艺）
        │  （① 包装交接包 packaging_package）
        ▼
链路 C 技术工艺（5 阶段 × 13 子步骤）
  任务接手 → 2.1 图纸八步 → 3.x 部件/排模/工艺 → 4.x 成本 → 5.x 报告发布
        │  （② 回传字段白名单 FINANCE_HANDOFF_FIELDS）
        ▼
  回填报价「产品行」→ 报价第 6 步出正式报价单
```

两条支线是「不能直接推进」的两处，做成支线而不是硬凑：
**支线 1** 正向报价第 1 步匹配不到标品（最高分 < 70）→ 工艺经理去技术工艺新建产品，再回第 1 步；
**支线 2** 技术工艺 2.2 做完工艺后，成本**不由工艺经理算** → 交财务经理测算，算完退回工艺经理复核。

## 1. 链路 A：正向报价（精准）

### 1.1 六步流水线（`cpq_wf.py::QUOTE_STEPS`）

| 步 | 名称 | 主责角色 | 这一步的产出 |
| --- | --- | --- | --- |
| 1 | 确认需求配置 | 销售经理 | 结构化需求 + 匹配到的标品 |
| 2 | 工艺确认 | 工艺经理 | **包装交接包 `packaging_package`**（盒型/尺寸/材料/成本/缺口/结果版本） |
| 3 | 定价-利润加成 | 销售经理 | 定价口径与加成 |
| 4 | 报价-其他加价项 | 销售经理 | 加价/折扣项 |
| 5 | 报价方案 | 销售经理 | **报价版本**（`QUOTE_VERSION_STEP = 5`）与「产品行」 |
| 6 | 输出报价单 | 销售经理 | 正式报价单（导出 / 写业务库） |

每一步都是**可回看、可留痕的快照**（`cpq_wf.step_snapshot(sid, n)`）。门禁只读已落地的快照，
**不做推断、不补默认值**。

### 1.2 需求怎么进来（第 1 步）

销售贴文字 / 传 Excel / PDF / Word / 图片 / 图纸，抽取规则是：

- 只从**明确标注且不歧义**的原文里抽（盒型编码、盒族、闭合方式、内尺寸、面纸克重、内托、V 槽、数量…）；
- **只填空字段**，不覆盖人工已填与 CAD 已填；每字段留 `user_text` 来源 + 原文证据 + 待确认标记；
- 同义表达等价（`225g面纸` ≈ `面纸225g`；`双开门` ≈ `对开`）；
- 原文与 CAD 冲突 → **两边证据都留、标冲突**，不静默覆盖。

### 1.3 第 3–6 步的门禁与「最后一公里」

- 第 3–6 步的完成门禁是**纯函数** `cpq_quote_gate.py`，被 Agent API 与卡片写接口共用（同一条判据）。
- 正式「最后一公里」（导出 Word `_build_quote_docx`、写业务库 `_import_quote`）走
  `_assert_formal_packaging_quote`：没有原会话号 / 原会话不是包装 / 成本包有缺口 / 成本证据有问题 /
  报价仍是草稿或 `publish_blocked` / 还有 `gap_count` —— 一律拒绝，返回 `formal_quote_blocked`。
- 语义：**带缺口的草稿可以内部预览、可以继续填；但导不出正式报价单、写不进业务库。**

## 2. 链路 B：快速报价（逆向）

### 2.1 为什么存在

当**没有完整工艺数据**（或不想为一次询价就走完技术工艺）时，从**标准报价案例库**里找相似案例，
销售挑一个基准，只改差异参数，直接出差异价。**全程停留在报价工作台，不进入技术工艺。**

### 2.2 流程

```
输入需求（文字/Excel/PDF/图片/DWG）
  → ① 识别包装关键参数（box_type / box_family / closure / 内尺寸 / 灰板 / 面纸 / 内托 /
        印刷 / 覆膜 / 烫金 / V 槽 / 磁铁 / 数量）
  → ② 查标准报价案例库：先按盒型与结构**硬筛选**，再按尺寸/材料/工艺/数量算**相似度**
  → ③ 返回 3~5 个候选：相似度、标准报价、报价日期、相同项、差异项、来源、是否已审核、排序理由
  → ④ **人工选一个基准案例**（系统只排序 + 给建议，不替用户决定）
  → ⑤ 在右侧字段工作区改少量差异参数（对比表：基准值 / 当前值 / 差异价）
  → ⑥ 计算差异价格 = 基准价 + 尺寸修正 + 材料修正 + 工艺增减 + 数量档修正 + 模具/版费修正 + 运输修正
  → ⑦ 生成快速报价（保留依据：基准案例号、基准价、修改项、每项加减、最终价、建议区间、
        预估偏差、有效期、规则版本）
```

### 2.3 两个入口的分工

| | 精准报价（链路 A） | 快速报价（链路 B） |
| --- | --- | --- |
| 数据来源 | 逐步建成本、工艺 | 标准报价案例库 |
| 是否进技术工艺 | 进（链路 C） | **不进** |
| 适用 | 新品 / 大单 / 要正式报价单 | 常做品类的快速估价 |
| 门槛 | 六步 + 正式门禁 | 命中已审核案例、盒型兼容、无未知特殊工艺、尺寸在阈值内、数量在区间内、案例未过期；**超出范围不硬算，提示转精准报价** |

## 3. 链路 C：技术工艺（五阶段 × 十三子步骤）

### 3.1 编号表（`workflow_stages.py`，后端唯一事实源）

| 阶段 | 标题 | 子步骤 |
| --- | --- | --- |
| 1 | 工艺评估需求 | 1.1 创建需求 · 1.2 确认需求 · 1.3 审核需求 |
| 2 | 图纸解析 | 2.1 图纸解析 |
| 3 | 组装与整合 | 3.1 整合图纸 · 3.2 参数推荐 · 3.3 组装工艺 |
| 4 | 成本测算 | 4.1 零件成本 · 4.2 组装成本 · 4.3 汇总 |
| 5 | 工艺评估报告 | 5.1 汇总结果 · 5.2 结果审核 · 5.3 发布并回传报价 |

### 3.2 为什么「表行序 ≠ 阶段号顺序」

图纸解析第 6 步 `field_write` 要把图纸读出的字段**回写进需求单**，所以它必须排在
**「1.1 创建需求」之后、「1.2 确认需求」之前**。原因：1.1 提交 / 1.2 通过 / 1.3 审核都会把需求
推离可编辑状态，先确认再解析必然踩 `REQUIREMENT_NOT_EDITABLE`。
所以用户顺着流程栏点下去的**实际顺序**是：创建需求 → 图纸解析 → 确认需求 → 审核需求 → …。
包装行业把第三阶段的页签改成 **3.1 方案与部件 / 3.2 排版排模 / 3.3 后道加工与组装工艺**（仅包装生效）。

### 3.3 任务卡与支线

技术工艺侧收到的是**带来源的卡片**（来源：报价 handoff / 成本任务 / 独立新建），任务类型决定是否推进报价步骤：

- **常规 handoff**：做完推进报价下一步；
- **支线**（`tech_new_product` / `tech_cost`）：做完只回结果，**报价卡片留在原步骤等**。

### 3.4 角色与可见范围

可见范围**按角色算**（`project_access.can_read()` / `visible_projects()`），不是全公司可见；
归档项目对非 owner 一律不可见。所以同一批数据里 `PE1`（工艺经理）看到 33 个、`FI1`（财务）15 个、
`SM1`（销售）可能只有 2 个 —— 这是设计，不是数据丢了。

## 4. 2.1 图纸解析：包装八步

### 4.1 八步（`packaging_drawing_flow/model.py::STEP_IDS`）

```
① file_preflight   文件预检      →  ② dwg_convert   DWG 转换（ODA 主 / 回退）
→ ③ cad_ir_parse   CAD 矢量解析  →  ④ packaging_semantics  包装语义识别
→ ⑤ parts_extract  零件提取      →  ⑥ field_write  字段回写需求
→ ⑦ pending_confirm 待确认生成   →  ⑧ downstream_prepare 下游任务准备
```

- **执行顺序即 `STEP_IDS`**；每步声明 `depends_on` 与 `produces`（`flow_plan()`）。
- `⑤ parts_extract` 内部有**两个子相位**（`geometry_regions_extract` → `business_parts_resolve`），
  但对外仍是**八步**，不许悄悄扩成第九步。
- **状态闭集**：`pending / running / completed / failed / blocked / unavailable / skipped`。
  其中 `blocked` **不是终态失败**（缺前置条件 ≠ 这步坏了），后续步骤照样要走到终态；
  真正的终态失败是 `failed / unavailable`（`STEP_TERMINAL_FAILURES`）。
- 一次解析的标识 `run_id = flow-<16 hex>`，由 `source_sha256 + drawing_version +
  requirement_snapshot_version + 规范化 prompt` 决定 —— **同一附件 + 同一需求快照 = 同一个 run**，
  所以重复点解析是「重放同一 run」，不是又开一个新 run。

### 4.2 三个层次的口径（最容易误解的地方）

| 层次 | 是什么 | 酒盒量级 |
| --- | --- | --- |
| **图元** | 线、弧、标注、文字 | 6711 个实体 |
| **几何区域 / 几何零件** | 按图元连通分量得到的封闭块 | 263 件 |
| **业务部件（业务件）** | 工程师口里的「左盖面纸、内托、磁铁」 | 28 件（待确认） |

**263 ≠ 28。** 当前口径：**业务件是成本、工艺、报告清单的唯一计件对象；几何区域只是证据。**
八步「8/8 completed」只代表**编排跑完**，不代表零件正确。
业务件的来源闭集是 `('dwg', 'missing')` —— **解析只吃 DWG**，不读工程师电脑里的 BOM/工艺文件。

### 4.3 语义层怎么做出「业务件」

图纸里没有「这是一件」的标记，系统靠多种线索合并判断（`packaging_semantics/`）：

- 名称锚点（`左盖面纸`）、材料标注（`225G铜版底PET光银`）、尺寸标注；
- 块路径、图层角色（`rules.py` 的 `match` 键是**闭集** `{names, name_prefix, name_contains}`，
  闭集外抛 `PACKAGING_LAYER_RULES_INVALID`，**不静默丢弃**）；
- 排版空间证据（同一排模里的重复副本不各算一件）。

产品上的交互水位：右栏给「业务部件」清单（默认图纸推导、标待人工确认）；每件最多 8 个 CAD 候选、
按可复算证据分排序、**未确认候选封顶 85%**（页面明写「这不是统计正确率」）；
最高分且图元完整、不与别件冲突的候选**自动归属**，但**尺寸仍需人工确认**；已有人工绑定不被自动覆盖。

### 4.4 「一件 = 多片」是常态

一个业务件在图纸里可能是几个**不相连**的闭合片段。规则：每片的 CAD ID / 图层 / 矩形 / 是否已确认都保留；
**不用并集矩形冒充零件外形**；不因多片而把 BOM 数量重复计；排版实例只是用量/版位证据，不是新增业务件。

## 5. 3.x 组装、排模、BOM、工艺路线与成本

### 5.1 各子步骤的产出与约束

| 子步骤 | 产出 | 关键约束 |
| --- | --- | --- |
| 3.1 方案与部件 | 业务部件清单（图纸推导，待确认） | 一件可由多片组成；同件只计一次 |
| 3.2 排版排模 | 排模记录（「各排 2 模」「纸张 860×460mm」） | **排模不是零件**；未确认的排模不进成本 |
| 3.3 后道加工与组装工艺 | 工艺路线（模切、糊盒、装配、检验…） | 缺组成/尺寸/费率**不伪造完整总额** |
| 4.1 / 4.2 / 4.3 | 零件成本 / 组装成本 / 汇总 | 单件只算材料费；整单走确定性公式 |

BOM 的行来源有三类：模板（`kb_packaging_part_template`）、几何回填（`dwg_parts`）、以及装配；
绑定时留痕 `size_source.dwg_binding`（含 `rule_id`）；**绑不上的行保持 `needs_input`** 并在 gaps 给
`part_size_unbound:<part_code>`，绝不硬猜尺寸。

### 5.2 两套数量、两套成本口径（关键）

- **两个「数量」必须分开**：**报价批量**（客户要多少）与**单件装配用量**（一件成品用几个）。
  不一致时变成**确认缺口**，不自动取一个。
- **单件成本**：包装走 `packaging_parts.load_part_cost(project_id, part_id)`，`cost_scope = "material_only"`，
  且要**校验业务件哈希**（`business_parts_hash` 对不上 → 当作没有成本，防止旧价冒充新价）。
- **整单成本**：走 `packaging_cost.load_cost()` 的确定性公式，**不重复叠加零件材料费**；
  `ready` 还要求 `has_gaps == False`。
- 计算对象是**业务件**：`cost_review.ir_from_packaging_parts()` 优先 `business_parts`；
  `parts_source()` 在包装行业**只认业务件**，清单为空或读取失败**不回退到几何碎片**。

### 5.3 公式引擎与模型：不分工，是分开的

成本计算里**没有模型调用**：

- 每条成本表达式登记 `variable_map`（语义名 → 表列字母）与 `source_formula`（原始单元格公式）；
  **源公式 / 变量映射 / 计算参数三者分开披露**——映射后等价 ≠「逐字照抄」，也 ≠ 材料价/单位/数量一定对；
- 求值是纯函数（`evaluate(expr, variables, precision)`），带精度参数、白名单函数、防注入；
- `verbatim_compare` 做「**变量映射后的**引擎表达式 ↔ 源表公式」等价比对 —— 证明的是**公式结构一致**；
- 模型只出现在**上游**（推荐零件名、判文字语义、推荐工序），它给的东西必须能被确定性链验证，**不能直接进价**。

一句话：**报价的钱是算出来的，不是模型说出来的。**

## 6. 两个交接包：A↔C 怎么串起来

### 6.1 报价 → 技术：`packaging_package`（第 2 步产出）

```
报价第 2 步（工艺确认）
  → packaging_package：盒型、尺寸、材料、成本、缺口、结果版本
  → cpq_tech_bridge.packaging_snapshot() 落成技术工艺能读的快照
      · s2_products     产品行
      · s2_packaging    盒型与参数
      · s2_packaging_cost 成本构成
  → 技术工艺按项目接手：零件 → BOM → 工艺路线 → 成本
```

### 6.2 技术 → 报价：字段白名单回传

`FINANCE_HANDOFF_FIELDS`（回传白名单）：
`business_case_id` `quote_session_id` `tech_project_id` `source_task_id` `industry` `quantity`
`unit_cost` `currency` `cost_status` `gap_count` `cost_fingerprint` `provisional`。

- **白名单的意义**：缺什么就进 `missing` **明说，不猜数**；报价侧据此落「产品行」（基础成本 + `provisional` 暂估标记）。
- 回传必须带 `cost_fingerprint`（这是哪一版成本）与 `provisional`（是不是暂估）。
- 内部草稿财务交接：`integration.send_to_finance(..., draft=True)` → `_send_packaging_finance_draft()`：
  仅包装可用；载荷带 `project_id`、需求事实、`business_parts_hash`、工艺路线；结果标 `draft=True`，
  `confirmed / params_confirmed / process_confirmed` 全 `False`、`waivers` 为空；写审计
  `packaging_finance_draft_handoff`；**不代签、不放行正式发布**。

### 6.3 成本有缺口时怎么走

可以走**「带缺口的内部草稿」**继续往下（销售能预览），但**正式导出 / 写业务库被服务端拦住**
（见 §1.3）。这条是「演示与内部评审能走通，但不能骗客户」。

## 7. 状态、版本与留痕怎么贯穿全程

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| 步骤快照 | `cpq_wf.step_snapshot(sid, n)` | 每步可回看；门禁只读它，不推断 |
| 报价版本 | 第 5 步落版（`QUOTE_VERSION_STEP`） | 第 6 步与导出消费**同一版** |
| 交接包 | 第 2 步 `packaging_package` | 包装链路的事实源 |
| 解析 run | `run_id = flow-<16 hex>` | 同附件+同需求快照 = 同一 run（重放而非新开） |
| 文档版本 | `meta_backend.get_doc/put_doc` + `MAX_VERSIONS` | 每个文档自己版本化，回滚切版本 |
| 成本指纹 | `cost_fingerprint` + `business_parts_hash` | 旧价/旧零件不许冒充当前 |
| 规则版本 | 成本规则快照 / `kb_version` | 「用的是哪一版规则」可追溯 |
| 草稿标记 | `draft_only` / `provisional` / `draft=True` | 草稿可点、可预览，但不等于放行审批 |

## 8. 端到端时序（文字版）

```
[销售] 报价首页 → 选行业(packaging) → 精准报价
   → 1 确认需求配置（文字/Excel/PDF/图片/图纸；只填空、留证据）
        ├─ 匹配到标品(≥70) → 继续
        └─ 匹配不到      → 支线1：工艺经理新建产品 → 回第 1 步
   → 2 工艺确认（工艺经理）→ 产出 packaging_package
        ▸ 交技术工艺（链路 C）
              1.1 创建需求 → 2.1 图纸八步 → 1.2 确认需求 → 1.3 审核需求
              → 3.1 部件 / 3.2 排模 / 3.3 工艺 → 4.1/4.2/4.3 成本
                   └─ 支线2：成本交财务经理测算 → 退回工艺经理复核
              → 5.1 汇总 / 5.2 审核 / 5.3 发布并回传报价
        ▸ 回传白名单字段 → 报价「产品行」（基础成本 + 暂估标记）
   → 3 定价-利润加成 → 4 其他加价项 → 5 报价方案（落报价版本）
   → 6 输出报价单（服务端门禁：有缺口/草稿/证据问题 → formal_quote_blocked）
   → 导出 Word / 写业务库

[销售] 快速报价（链路 B，不进技术工艺）
   → 输入需求 → 识别关键参数 → 查标准案例库（硬筛选 + 相似度）
   → 人工选基准案例 → 改差异参数（右侧工作区）→ 算差异价 → 生成快速报价
        └─ 超出阈值 → 提示「建议转精准报价」，数据带入链路 A，不重输
```

## 9. 一句话记住每段

- **链路 A** 是「六步卡 + 快照 + 正式门禁」：责任按角色交替，**带缺口能预览、出不了正式单**。
- **链路 B** 是「相似案例 + 人工选基准 + 差异价」：快，但**只在范围命中时成立**，超界就转 A。
- **链路 C** 是「五阶段 × 十三子步骤」：行序按**依赖**排，`field_write` 必须夹在 1.1 与 1.2 之间。
- **2.1 八步** 是「预检 → 转换 → IR → 语义 → 零件 → 回写 → 待确认 → 下游」：只吃 DWG，
  产出**业务件**；几何区域只是证据。
- **两个交接包**（`packaging_package` 去、`FINANCE_HANDOFF_FIELDS` 回）是 A↔C 的唯一通道，
  靠 `cost_fingerprint` / `business_parts_hash` / `provisional` 保证「不拿旧价当新价、不拿暂估当正式」。
- **钱是算出来的**：成本是确定性公式 + 业务件；模型只在上游推荐，不进价。
