# 2.1 零件刷新只接受最新一轮读取

状态：Spec + 红测（实现中）
红测：`tests/test_packaging_parts_refresh_latest_request_wins_red.py`

## 症状与根因

进入项目时 `openProject()` 会异步读取包装几何零件与业务部件；图纸解析结束后会再发起
一轮读取。两轮请求可重叠。当前只有项目 ID 守卫，没有同项目内的请求先后守卫，因此打开页
时的旧空结果可能晚于解析后的新结果返回，并覆盖内存数据与左栏 DOM。切换页面重进会再读
最新持久化版本，所以零件又出现。

## 目标与规则

1. 每次包装零件读取（进入页、解析完成、分页、写后重读）取得单调递增的读取序号，并绑定
   发起时的项目 ID。
2. 只有项目 ID 与读取序号都仍是最新的响应，才能更新 `currentPackagingParts`、
   `currentPackagingBusinessParts`、`packagingPartsShown`、读取阶段状态或调用 `renderTree()`。
3. 几何零件与业务部件并行读取时，共享同一读取序号；其中一个旧响应不得覆盖另一个新响应
   的结果。过期响应不得清空已显示的列表，也不得写入“读失败”空态。
4. 解析结束发起的新读取使进入项目时的旧读取失效。过期补充任务不得覆盖最新数据；补推导
   与自动绑定仍保持幂等，不能因竞态重复生成历史版本。
5. 当前读取失败时，既有 read_problem / 错误文案与几何、业务两路独立失败处理保持不变；
   读取序号只负责阻止过期结果，不吞掉当前请求的真实失败。
6. 项目切换继续由项目 ID 守卫隔离；新项目请求不受旧项目响应影响。

## 验收

- 先启动进入页读取 A，再启动解析完成读取 B；B 返回 28 个业务件后，A 返回空结果，最终
  内存与 DOM 仍显示 B 的 28 件。
- A 的过期网络错误不得清空 B 已显示的件数或标成当前读取失败。
- 最新请求自身失败时仍显示原有读取失败文案。
- 项目从 P1 切到 P2 后，P1 的迟到响应不得渲染进 P2。
- 写后重读、分页、并行几何/业务读取和既有空态语义回归通过。

## 验证边界

用本地前端函数与可控延迟响应做确定性测试；不连接线上服务、不调用模型、不改业务数据。
此 Spec 不授权提交、推送或部署。
