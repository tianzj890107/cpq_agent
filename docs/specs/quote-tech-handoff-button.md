## 1. 现场问题（实测，不是推断）

销售在报价工作台走一条包装询盘（数码天地盒 100*90*40 / 铜版纸+亮膜+哑膜 / 灰板 2.5mm /
首批 1500 / 常温），走到第 2 步「工艺确认」就卡住，用户原话是
**「想走技术工艺流程但是走不过去」**。

现场链路（与用户截图逐条对应）：

1. 第 1 步匹配把这条包装需求拿去查**锂亚电池**库，Top3 是
   `91000226 / 91000255 / 91000365`，「用途/场景契合」维度只有 30 分、总分 86 分。
2. 用户在对话里明确选了「转定制评估」——但这句选择**只是一个字符串**：
   `cpq_agent_server.py` 全文只在文字里说「建议转入定制评估」（`:663` `:832` `:1179` `:1887`），
   没有任何结构化字段、没有建任务、没有状态变更。用户以为选了路，系统侧什么都没发生。
3. 用户点「进入下一大步骤」→ 第 2 步两张表 **共 0 条**（非标没有标品，`CARRY_MAP` 沿用为空）；
   点「强行填满本步骤」也无效（第 2 步是人工核对步骤，智能体不渲染）。
4. 技术工艺那边收不到任何任务——整条链路上**没有一个可以让用户主动发起「新增工艺」的按钮**。

### 1.1 根本症结：能力早就有了，缺的是一个看得见的入口

| 既有资产 | 位置 | 现状 |
| --- | --- | --- |
| `tech_new_product` 任务类型 | `cpq_wf.py:52` | 已有；默认收件角色 `process_mgr`；支线，不推进报价步骤 |
| 新增工艺专属页 | `tech_app/frontend/tech-task.js` | 已有：上传图纸 → 建单 → 1.1 → 2.1 |
| 技术工艺待办入口 | `tech_app/frontend/cpq-tech-inbox.js:179` | 已有：`tech_new_product` → 工艺经理领取 |
| 回写报价 | `cpq_tech_bridge.py:766` `send_to_quote()` | 已有：工艺出方案后落回报价会话 |
| 转交弹窗里的「新增工艺」选项 | `确认需求解析结果.html:3329` | 已有 |
| **报价工作台按钮区的常驻按钮** | —— | **缺** |

现有入口的两个毛病：

- 唯一的建议气泡 `showTechNewSuggestion()`（`:3220`）只在
  `确认需求解析结果.html:2381` `if (d.below_threshold)` 时触发 —— 本次 86 分 ≥ 阈值 70，
  气泡和按钮**都不出现**；
- 页脚「转交任务」按钮（`:798`）的预选值同样只看 `below`（`:3289`），
  而且它是通用转交入口，用户不知道要在这个弹窗里把「转交目的」改成「新增工艺」。

**本批只做一件事**：在报价工作台的按钮区加一个常驻按钮，让用户在任何时候都能主动
把这单转给技术工艺做「新增工艺」。不改匹配算法、不改门禁、不改定价。

## 2. 目标（本批唯一验收点）

报价工作台聊天输入框正上方的按钮区（`<div class="quick-actions" id="quickActions">`，
现有「强行填满本步骤 / 进入下一大步骤 / 上一步 / 转交任务」四个按钮的那一排）新增第五个按钮：

```html
<button class="quick-action-btn" id="qaTechNew"
        onclick="wfOpenSend(false, 'tech_new_product')">
  <i class="ti ti-tools"></i> 转技术工艺
</button>
```

点它 → 打开既有的转交弹窗，且「转交目的」已预选「新增工艺」、建议收件角色已是工艺经理；
用户确认收件人后点「发送」，报价卡片**停在当前步骤**，工艺经理在技术工艺侧领到这条任务。

## 3. 接口契约（实现提示词的验收依据）

### 3.1 位置与外观

1. 按钮必须落在 `#quickActions` 容器内（与既有四个按钮同一排）；不得新开一排、
   不得塞进下拉菜单、不得只做成链接。
2. `class="quick-action-btn"`，与其他快捷按钮同款；带 Tabler 图标（`<i class="ti ti-...">`）。
3. 文案固定为 **「转技术工艺」**（业务用户视角；不要写成「新增工艺」这种内部术语，
   也不要用英文）。
4. `id` 固定为 `qaTechNew`，全页唯一。

### 3.2 点击行为

```js
onclick="wfOpenSend(false, 'tech_new_product')"
```

必须逐字复用既有的 `wfOpenSend(forced, presetKind)`：`forced=false`（不是强制交接）。
**不新增发送逻辑、不新增后端接口、不改 `cpq_wf`。**

### 3.3 常驻可用

- 按钮**不依赖匹配结果**：所在标签里不得出现 `below_threshold` / `nonstandard` /
  `WF.matchResult` —— 用户自己判断得出「这单要走新工艺」的时候，按钮就得在。
- 按钮**不依赖当前步骤**：第 1～6 步都可见可用。
- 禁用规则与同排按钮一致：由 `setBusy()`（`确认需求解析结果.html:2484` 附近）统一按
  `lock = busy || GATE_BLOCKED` 禁用；未登录时随其他快捷按钮一起禁用，
  不得绕过登录直接发任务。
- 按钮标签里不写 `disabled` 属性。

### 3.4 发送闭环（复用既有行为，不许退化）

点「发送」后必须依次满足：

1. 先出用户气泡（既有 `beginUserTurn` 路径，`:3444-3447`）；
2. 产生一条 `task_kind=tech_new_product` 的任务，收件角色默认工艺经理；
3. 会话里出 AI 回执「已发起「新增工艺」任务 …」（`:3450-3453`）；
4. 报价卡片**停留在原步骤**，文案「本报价卡片仍停在第 N 步，不受影响」保留；
5. 任务携带 `techNewPayload()`（需求正文 + 文档摘要 + 匹配结果），工艺经理不必回头翻会话。

### 3.5 绝不编造业务数据

- 该按钮**不得**写入 `s1_products` / `s1_techparams`：非标定制没有成品编码，
  塞假产品行是明确禁止的。
- 不得修改 `s1_basic` 的任何字段值。
- 不得为了让流程继续而生成占位成品编码。

- 不新增第三方依赖；不改 `cpq_wf` 的任务类型与默认角色。
- 不改半导体/电池/电器的三项门禁，也不改 `industry_templates.required_keys('packaging')`。
- 不改 `RECOMMEND_THRESHOLD`（70）、不改六维权重与打分函数。
- 不改动既有四个快捷按钮的 `id` 与 `onclick`。
- 不删除或改写历史会话、卡片、任务、证据；不调用删除/重置接口。

## 6. 本批不做（已分析、留待后续）

同一现场还暴露了三个更深的问题，**不在本批范围**，先记录清楚，避免以后重新排查：

1. **非标判定只看总分阈值**（`cpq_match.py:293` `below = best < 70`）。
   本次总分 86，但「用途/场景契合」维度只有 30 分 —— 维度塌陷被其他维度满分掩盖，
   `below_threshold=False`，系统不知道这单其实接不住。
   后续应新增一条**不看总分**的维度下限配置（如 `NONSTANDARD_DIM_FLOORS = {"scope": 60}`），
   并让 `match()` 返回结构化的 `nonstandard`，供建议气泡与门禁复用。
2. **第 2 步「工艺确认」缺少非标分支**。非标没有标品 → `carryProducts()` 的
   `if (!rows.length) return;` 让两张表永远停在 0 条，也没有「定制技术要求」的承载位。
   后续应新增 `s2_custom_spec` 分区，把第 1 步的定制要点变成工艺经理可核对的明确对象。
3. **第 3 步门禁文案归因错误**。`runMarkupStep()` 取不到产品行时只报
   「前面步骤还没有产品信息。」——对非标定制来说原因不是「没填」，而是「库里没有对应标品」，
   而且不给任何可执行动作。
4. 智能体在 `s1_basic` 里批量写入带「（推荐）」的业务值（税率/币种/付款 30-60-10 等），
   是否越权属第 5 批「不为通过流程填充 mock 业务值」口径，另行评估。
