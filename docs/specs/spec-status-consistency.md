# 规格：Spec「状态」行与红测实际状态一致（快速报价系列）

状态：Spec + 红测（**未实现**）
红测：`tests/test_spec_status_consistency_red.py`
范围：`docs/specs/quick-quote-*.md`（当前 13 份，含批 1–13；其他目录下的 Spec 不在本批范围）。

## 0. 为什么有这一条（实测，不是推断）

2026-09-21 夜间出现了一次真实的漂移：`docs/specs/quick-quote-10-material-gsm-attribution.md`
头部写着「状态：**待实现**（红测先写、先跑红）」，而它的 37 条红测**已经全绿**（实现者当场改成
green 了，Spec 头没跟着改）。同一时刻的全量清单里，同一系列还有 9 份 Spec 写着「未实现」而红测
早已全绿。

后果不是"文档不好看"，而是**判断依据失真**：

- 人（和 Agent）按 Spec 头判断"这批还没做"，于是重复排查、重复写红测，或者把已实现的能力
  当成缺口汇报；
- 反过来，如果哪天有人把已实现的能力按"未实现"归档，能力声明就会与事实不符。

## 1. 契约

### 1.1 状态行必须用两个合法字面量之一

`docs/specs/quick-quote-*.md` 里**第一处**以 `状态：` 开头的行（允许前缀 `- `）去掉 `**` 之后，
必须以这两个字面量之一开头：

```
状态：Spec + 红测（未实现）
状态：Spec + 红测（已实现）
```

- 后面允许追加说明（例如 `状态：Spec + 红测（已实现）（9-21 落地；…）`）；
- **不许**再出现「待实现」「Spec（未实现）」「Spec + 红测 + 实现」这类等价但不同形的写法
  （机器读不了、人也会读错）；
- 判定方式一律取**含「未实现」= 未实现**、否则视为已实现。

### 1.2 必须能解析出红测文件

同一份 Spec 里必须有一行 `红测：`，其反引号里给出的路径必须真实存在（相对仓库根）。

### 1.3 声明必须与红测的实际结果一致

- 声明**未实现** → 该 Spec 的红测文件当前必须有**失败**（`unittest` 非零退出）；
- 声明**已实现** → 该 Spec 的红测文件当前必须**全绿**（零退出）。

判据是"跑一遍"，不是"看代码像不像"——本批要防的正是"看着像还没做、其实早做完了"。

### 1.4 现有 13 份需要做的只是把状态行改成合法字面量（不改任何红测）

批 1–9 实际已实现（红测全绿）→ 状态行改成 `状态：Spec + 红测（已实现）`；
批 12 / 13（本次新写、红测仍红）保持 `状态：Spec + 红测（未实现）`。

## 2. 红测映射（`tests/test_spec_status_consistency_red.py`）

| 组 | 覆盖 |
| --- | --- |
| A | 每份 `quick-quote-*.md` 都能解析出状态行，且字面量合法 |
| B | 每份都能解析出 `红测：` 路径，且文件存在 |
| C | 声明与实际一致：未实现 → 红测必须失败；已实现 → 红测必须全绿 |

## 3. 非目标

- 不改任何红测文件，也不改任何实现；
- 不要求其他目录（`docs/specs/tech-*.md` 等）的 Spec 跟上（历史存量，另批再收）；
- 不把"状态"做成自动生成的索引（本批只要求字面量与事实一致，避免再造一份事实源）。
