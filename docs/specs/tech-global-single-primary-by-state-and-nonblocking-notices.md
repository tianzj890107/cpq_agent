# 技术工艺全流程：每页签每状态唯一主按钮、贴底说明与不阻塞权限提示

状态：TDD Red，等待 DeepSeek 实现。

## 1. 产品目标

技术工艺九阶段的每个用户可见页签，在每个稳定业务状态下必须有且仅有一个主按钮。
主按钮不是固定按钮名，而是当前最应该完成的下一件事：执行前是“一键生成/解析/测算”，
执行成功后切换为“确认/提交/进入下一步”。视觉统一采用当前“开始整合分析”的蓝色渐变
主按钮；其它同时可见动作一律为 aux/次按钮。

此外恢复“会话绑定当前项目；右侧工作台只承载业务步骤，不重复会话。”说明，但不能重新
把已经贴底的输入框向上顶。权限/只读提示不得以普通文档流顶部横条挤压看板和底栏。

## 2. 唯一主按钮通用契约

- “可见动作”按 `getState().visible !== false` 判定；其中 `role === 'primary'` 必须恰好一个。
- busy、无权限、缺数据时主按钮仍保持唯一主按钮身份；可以 disabled，或按现有“点了再给
  真实原因”策略保持可点，但不能因为不可执行就把两个按钮都变 aux 或同时变 primary。
- 主按钮切换必须来自既有真实业务状态，不得靠点击后的本地布尔值冒充完成。
- 父壳只渲染看板动作快照，不按动作名猜测主按钮，也不在多 primary 时随便取第一个。
- `TechBoardRuntime` 在开发/测试环境应能对动作快照验证 `visible primary count === 1`，异常
  输出明确的 stage/view/action 诊断；业务页面本身必须消除异常，不能靠父壳吞掉。

## 3. 九阶段与页签状态矩阵

| 阶段/页签 | 执行前唯一主按钮 | 执行后唯一主按钮 |
| --- | --- | --- |
| 1.1 `requirement-create` | 一键解析需求 | 提交确认 |
| 1.2 `requirement-confirm` | 通过确认 | 已确认后进入审核（若动作完成即导航，则导航前保持“通过确认”busy） |
| 1.3 `requirement-review` | 提交审核意见 | 审核完成后进入图纸解析（同上，完成即导航） |
| 2.1 `drawing` | 一键解析图纸 | 确认解析结果并进入下一步 |
| 2.2 `process/drawings` | 一键分析整合图纸 | 确认图纸并进入参数推荐 |
| 2.2 `process/params` | 一键生成参数推荐 | 确认并进入下一页签 |
| 2.2 `process/process` | 一键生成组装工艺 | 确认并进入下一步 |
| 2.3 `cost/parts`、`assembly`、`total` | 一键测算全部成本 | 确认成本 |
| 3.1 `summary` | 一键生成报告草稿 | 提交审核 |
| 3.2 `report-review` | 审核通过并进入下一步 | 完成即导航到发布阶段 |
| 3.3 `report-publish`（approved） | 发布报告 | — |
| 3.3 `report-publish`（published） | 回传销售经理继续报价 | 回传保持幂等；新建版本为次按钮 |

“保存草稿、驳回、退回、重新生成、更新字段、联网核验、更多功能、回传/写库中的非当前
下一步动作”保留为次按钮或更多功能，不能与当前主按钮同时使用 primary。

## 4. 主按钮视觉

唯一主按钮继续由 `#techChatPrimary` 承载，并采用与“开始整合分析”相同的：

- `var(--gradient-primary)`、白字、透明边框；
- hover 为 `var(--gradient-primary-hover)`；
- 统一胶囊圆角、字号和高度；
- disabled 仍可识别为本状态主动作，但不得出现第二颗蓝色主按钮。

右侧嵌入页的重复 footer 主按钮继续隐藏，操作入口仍集中在左侧会话操作栏。

## 5. 会话说明与输入框贴底

- 恢复原文：`会话绑定当前项目；右侧工作台只承载业务步骤，不重复会话。`
- 为同时满足“保留说明”和“输入框仍贴底”，说明不得作为输入框下方的普通流内容；应在
  composer 内以不占布局高度的辅助提示呈现，推荐绝对定位在输入框上方，或放入不改变
  输入框底边坐标的既有区域。
- `#techChatPane .oc-composer` 继续 `padding: 10px 16px 0`；输入框底边位置不得回退。
- 紧凑按钮、12px 输入文字、按行自增高、120px 上限均保持。

## 6. 权限提示不阻塞布局

### 技术工艺

继续使用 `#techContextNotice`，它位于既有 `.tech-workspace-context` 标题行：单行省略、
不增加独立横条、不改变 `#techWorkspaceOutlet` 和 `.tech-workbench-bottom` 的 flex 布局。

### 报价

现有 `wfRenderBar()` 动态创建 `#wfBar` 并 `insertBefore(bar, resultsContent)` 的普通流实现
必须清理。未登录、无权限、待领取和可编辑提示应复用既有固定标题/状态区域或不占布局的
overlay/status chip；不能改变 `resultsContent` 高度，不能覆盖表格，不能使上下步按钮移出
可见区域。权限后端校验和按钮禁用逻辑保持不变。

## 7. 禁止事项

- 不新增第二套业务接口、算法、状态库或导航协议；
- 不删除任何现有业务动作，只调整 label/role/visible 及必要的“确认并进入下一步”组合动作；
- 组合动作必须复用既有确认接口，确认成功后才走 `TechEmbed.requestNavigate`；
- 不放宽权限，不用本地状态冒充完成，不改历史数据；
- 不把提示移到会话消息里反复生成；不以 `display:none` 直接丢掉权限信息。

## 8. 验收

1. 九阶段、2.2 三页签、2.3 三页签与报告状态全部有明确状态主按钮矩阵。
2. 每个可达稳定状态的可见 primary 数严格等于 1。
3. 主按钮文案从“执行”按真实完成态切成“确认/提交/下一步”。
4. 主按钮视觉与开始整合分析一致。
5. 会话绑定说明存在，但技术输入框底边坐标与当前贴底实现一致。
6. 技术提示留在标题行；报价不再动态插入普通流 `#wfBar`。
7. 上一步/下一步 footer 始终是结果卡的固定 flex 子项，权限提示和长内容都不能挤掉它。
