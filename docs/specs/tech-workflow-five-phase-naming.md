# 技术工艺全局口径修正：五阶段 + 子步骤编号（批次 5A）

状态：Spec + 红测（已实现）
红测：`tests/test_tech_workflow_five_phase_naming_red.py`

## 1. 背景与真实问题

技术工艺工作台现在的「阶段口径」有三套并存，互相打架：

1. **顶部流程条**（`tech-workbench.js` 的 `MAJOR_STEPS`）已经是 5 个大流程：
   1 工艺评估需求 / 2 图纸解析 / 3 组装与整合 / 4 成本测算 / 5 工艺评估报告。
2. **内部 stage 编号**（同一个文件的 `STAGES[].no`）还是老的九阶段号：
   `1.1 1.2 1.3 / 2.1 / 2.2 / 2.3 / 3.1 3.2 3.3`，其中 `process`（组装与整合）叫 **2.2**、
   `cost`（成本测算）叫 **2.3**、`summary / report-review / report-publish`（工艺评估报告）
   叫 **3.1 / 3.2 / 3.3**。`STAGES[].phase / phaseTitle` 还是更老的三阶段标题
   （接受工艺评估需求 / 解析技术工艺过程 / 输出工艺评估结果）。
3. **散落的旧文案**：页面标题、页签行、右上角小标题、会话卡片结论、Agent 提示词与报错
   都还在用上面那套编号，例如 `2.2 组装与整合`、`2.3 成本测算`、`3.1 汇总结果`、
   「九阶段白名单」，以及 `2.1 图纸解析 → 2.2 组装与整合 → 2.3 成本测算` 这种三阶段页签行。

结果：同一个页面，顶部说「第 3 阶段 组装与整合」，页内页签行说「2.2 组装与整合」；
`cost` 页顶部是「第 4 阶段」，页内是「2.3 成本测算」；报告三步在顶部是「第 5 阶段」，
页内是「3.1 / 3.2 / 3.3」。用户看到的编号自相矛盾，也会把「第 3 大步」误解成报告阶段。

本批只修**口径**：让「阶段号 + 子步骤号 + 标题」在全部用户可见处与 Agent 可用处**只有一个来源、一套编号**。
本批不实现批次 5B 的统一流程状态机与门禁（那是下一批）。

## 2. 规范口径（唯一事实源）

**5 个阶段，13 个子步骤。** 阶段号与顶部流程条一致；子步骤号是「阶段号.序号」。

| 阶段 | 阶段标题 | 子步骤 | 子步骤标题 | stage id | 页签 view |
|---|---|---|---|---|---|
| 1 | 工艺评估需求 | 1.1 | 创建需求 | `requirement-create` | — |
| 1 | 工艺评估需求 | 1.2 | 确认需求 | `requirement-confirm` | — |
| 1 | 工艺评估需求 | 1.3 | 审核需求 | `requirement-review` | — |
| 2 | 图纸解析 | 2.1 | 图纸解析 | `drawing` | — |
| 3 | 组装与整合 | 3.1 | 整合图纸 | `process` | `drawings` |
| 3 | 组装与整合 | 3.2 | 参数推荐 | `process` | `params` |
| 3 | 组装与整合 | 3.3 | 组装工艺 | `process` | `process` |
| 4 | 成本测算 | 4.1 | 零件成本 | `cost` | `parts` |
| 4 | 成本测算 | 4.2 | 组装成本 | `cost` | `assembly` |
| 4 | 成本测算 | 4.3 | 汇总 | `cost` | `total` |
| 5 | 工艺评估报告 | 5.1 | 汇总结果 | `summary` | — |
| 5 | 工艺评估报告 | 5.2 | 结果审核 | `report-review` | — |
| 5 | 工艺评估报告 | 5.3 | 发布并回传报价 | `report-publish` | — |

两条派生规则：

* **stage 与子步骤的关系有两类**：`process` 与 `cost` 各自**跨 3 个子步骤**（由页内页签决定
  当前子步骤），其余 7 个 stage 与子步骤 **1:1**。
* **称呼规则**：一个 stage 1:1 对应子步骤时，用户可见文案用「子步骤号 + 子步骤标题」
  （如 `2.1 图纸解析`、`5.1 汇总结果`）；一个 stage 跨多个子步骤时，用「阶段号 + 阶段标题」
  （如 `3 组装与整合`、`4 成本测算`），页内再用子步骤号区分页签。
* 「第 N 大步」一律改称「第 N 阶段」。

## 3. 用户角色与用户故事

* 作为工艺工程师，我在任何一页看到的同一步编号必须一样，页内页签行的「3.2 参数推荐」
  必须就是顶部「第 3 阶段 组装与整合」里的那一步。
* 作为财务经理，我打开成本页时看到的是「4 成本测算 / 4.1 零件成本 / 4.2 组装成本 /
  4.3 汇总」，不是「2.3 成本测算」。
* 作为工艺经理，报告三步在顶部是第 5 阶段，页内就必须是 5.1 / 5.2 / 5.3。
* 作为使用者，我在会话里问「现在第几步」，Agent 说的编号要和我屏幕上一致。

## 4. 当前流程

1. 顶部流程条按 `MAJOR_STEPS` 渲染 5 个大流程按钮；子步骤只在阶段 1、5 的标题行以
   「创建 / 确认 / 审核」「汇总结果 / 结果审核 / 发布并回传报价」按钮呈现（不带编号）。
2. 阶段 3、4 的子步骤由 `CHILD_TAB_PROXY` 注册成 `data-child-tab` 按钮，只有 `label`，
   没有编号。
3. 各页页内的旧页签行（`index.html` / `assembly-integration.html` / `cost-review.html`）
   仍写死 `2.1 图纸解析 → 2.2 组装与整合 → 2.3 成本测算` 这类三阶段文案。
4. `summary-result.js`、`report-publish-result.js`、`workflow.js` 各自渲染一套「1 / 2 / 3」
   三阶段流程条，子步骤写 `3.1 汇总结果 / 3.2 审核报告 / 3.3 发布报告`。
5. `workflow-navigation.js` 的 `stages` 表是流程栏跳转与门禁的「唯一事实源」，
   键是老的 `1.1/1.2/1.3/2.1/2.2/2.3/3.1/3.2/3.3`。
6. 后端的 Agent 提示词写着「九阶段落点表」并列出 `1.1 / 1.2 / 1.3 / 2.1 / 2.2 / 2.3 / 3.1 / 3.2 / 3.3`；
   越界报错是「不在九阶段白名单内」（`oc_agent.py`、`tech-board-runtime.js`）。

## 5. 目标流程

1. 前端只保留**一份**口径表（`tech-workbench.js` 的 `STAGES` 扩展为「阶段号 + 阶段标题 +
   子步骤号 + 子步骤标题 + 页签 view」），顶部流程条、子步骤按钮、页签代理、Agent 上下文
   全部从它派生，不再各自写死编号。
2. 后端新增**一份**对应口径表（`tech_app/backend/services/workflow_stages.py`），Agent 提示词、
   白名单报错、阶段标题都由它生成；两边的 (stage id, 阶段号, 子步骤号, 标题) 必须逐行一致。
3. 所有用户可见处改用规范口径；旧的 `2.2 / 2.3 / 3.1 / 3.2 / 3.3` 与「九阶段」「第 N 大步」
   在技术工艺范围内不再出现。

## 6. 状态定义及状态转换

本批不引入新状态：`stage` 的取值集合、URL 参数、页面的进入/退出条件都不变（见第 12 节）。
新增的只有**编号与标题**这一层投影。

## 7. 接口与数据契约

* 前端口径表条目（`tech-workbench.js`）：至少含
  `{ id, phase, phaseTitle, sub, subTitle, label, page }`，取值就是第 2 节的表；
  阶段 3、4 的页签表（现有 `CHILD_TAB_PROXY`）条目必须补 `no` 与 `stage` 字段，取值
  `3.1/3.2/3.3` 与 `4.1/4.2/4.3`。
* 后端口径表（新模块 `tech_app/backend/services/workflow_stages.py`）：导出
  `PHASES`（5 条：`no / title / subs`）与 `STAGES`（13 条：`sub / title / stage_id / view`），
  以及 `stage_title(stage_id)` / `sub_of(stage_id)` 这类查表函数。
* `page_context`（发往模型的阶段语义）：1:1 的 stage 用「子步骤号 + 子步骤标题」
  （`2.1 图纸解析`、`5.2 结果审核`…）；跨子步骤的 stage 用「阶段号 + 阶段标题」
  （`3 组装与整合`、`4 成本测算`）。9 个 stage 的取值必须互不相同，且查不到时返回 `null`，
  不得回退成任何别的步骤（保留既有能力）。
* 不新增、不改动任何 HTTP 接口；不新增字段到业务文档；不改数据库。

## 8. 正常路径

1. 用户打开任一页：顶部流程条显示 5 个阶段；页内页签行显示该阶段的子步骤号；
   页内小标题显示的阶段号与顶部一致。
2. 用户在阶段 3 的页签间切换：页签文案 `3.1 整合图纸 / 3.2 参数推荐 / 3.3 组装工艺`，
   高亮跟随当前页签。
3. 用户在报告页：页内流程条是 5 个阶段，第 5 阶段的子步骤是 `5.1 汇总结果 / 5.2 结果审核 /
   5.3 发布并回传报价`，高亮跟随当前页。
4. 用户问 Agent「这是什么步骤」：Agent 按后端口径表回答，编号与屏幕一致。

## 9. 异常路径

* 后端口径表查不到某个 stage（例如历史 URL 带了已退役的 stage）：返回空标题，
  **不得**退回默认步骤（不得再出现「默认 2.1 图纸解析」这类兜底）。
* 前端口径表缺项时，页面按「不带编号的标题」渲染，不得显示旧的 `2.2 / 2.3` 编号。

## 10. 并发与幂等

本批是纯静态口径与文案投影，不涉及写库、任务与并发；重复刷新同一页面必须得到同一编号。

## 11. 刷新、重试、重复点击和服务重启后的行为

* 刷新页面后编号不变（口径来自静态表与 URL，不来自服务端缓存）。
* 服务重启后编号不变（后端口径表是代码，不是数据）。

## 12. 权限边界

不改任何权限判定。阶段 4 仍是财务经理的步骤、阶段 1.3/5.2 仍由有权限的人提交，
编号变化不影响 `required_role` 判定。

## 13. 历史数据兼容

* **stage id 一律不改**（`requirement-create` … `report-publish` 九个），页面文件名、
  URL 上的 `stage=` 与 `task_id=`、iframe 嵌入参数、`tech-board-*` 消息协议里的 `stage`
  全部保持原值 —— 历史链接、历史会话、历史任务、已嵌入的页面都不受影响。
* 会话时间线、审计、任务 payload 里既有的 `page_context` 文本**不迁移、不改写**：
  历史记录保持原样，只保证新记录用新口径。
* 不删除、不清空任何数据。

## 14. 非目标

* 不做批次 5B 的统一流程状态机、阶段完成条件与准入门禁（下一批做，本批只出编号）。
* 不改业务流程、不改门禁强度、不改权限、不改任何接口与数据结构。
* 不改上游 `tech_app/backend/config.py` 的 `TECH_SUBSTEPS`（那是材料/制造/清洗等上游六子步骤
  的另一套口径，与本批无关）。
* 不改 `cpq_wf.QUOTE_STEPS`（报价 6 步，属于报价侧口径）。
* 不做视觉重设计：只改编号与标题文案，样式、布局、DOM 结构保持原样。

## 15. 可自动化验收标准

1. 前端口径表与第 2 节的 13 行逐行一致（stage id、阶段号、阶段标题、子步骤号、子步骤标题）。
2. 顶部 5 个阶段标题与第 2 节一致。
3. 阶段 3、4 的页签表带 `3.1/3.2/3.3` 与 `4.1/4.2/4.3` 编号且标题一致；
   阶段 1、5 的子步骤按钮标题一致。
4. 9 个 `page_context` 取值互不相同、符合第 7 节规则；查不到返回 null 且不退回别的步骤。
5. 后端口径表存在且与前端逐行一致；Agent 提示词与白名单报错由它生成。
6. 用户可见处不再出现旧编号与旧称呼：
   `2.2 组装与整合`、`2.3 成本测算`、`3.1 汇总结果` / `3.2 审核` / `3.3 发布`（作为报告三步）、
   `2.1 图纸解析 → 2.2 … → 2.3 …` 的三阶段页签行、「九阶段」、「第 N 大步」。
7. 报告三页（汇总/结果审核/发布）与组装、成本页的页内流程条渲染的是 5 个阶段，
   第 5 阶段的子步骤是 `5.1/5.2/5.3`。
8. 护栏：9 个 stage id、页面文件名、URL 参数、`TECH_SUBSTEPS`、`QUOTE_STEPS` 全部不变。

## 16. 人工验收场景

1. 依次打开 1.1 → 1.3、2.1、组装页三个页签、成本页三个页签、5.1 → 5.3，
   确认顶部与页内编号始终一致，不存在 `2.2` / `2.3` / `3.1` 这类旧编号。
2. 打开一个历史项目（旧链接带 `stage=`）：页面能打开、编号是新的、数据不变。
3. 打开会话时间线里的历史记录：历史 `page_context` 文本保持原样，不清空、不改写。
4. 问 Agent「现在第几步」：回答的编号与屏幕一致；故意给一个不存在的 stage，
   报错用新称呼且不退回别的步骤。

## 17. 不允许减少的既有能力

* 9 个 stage id 与页面映射、iframe 嵌入协议、同源校验、`data-child-tab` 代理点击。
* `STAGE_AGENT_CONTEXT` 每个 stage 的独立性：互不相同、查不到返回 null、不回退。
* `workflow-navigation.js` 的跳转校验与门禁语义（只是换编号，不放宽也不收紧）。
* 阶段 5 与「已回传报价」是两个可区分状态（本批只保证文案可区分，状态机在 5B）。
* 顶部流程条的禁用逻辑（无项目时可看不可点）。
