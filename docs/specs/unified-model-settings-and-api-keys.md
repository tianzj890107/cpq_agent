# 报价与技术工艺统一模型配置、API Key 和设置弹卡 Spec

## 1. 目标

配置报价 CPQ 只保留一套模型设置。报价助手现有模型配置是唯一事实源；配置助手、规则助手和技术工艺不得再维护第二份模型选择、生成参数或 API Key。

所有“设置”按钮和页头模型名称都打开同一种居中模态卡片，不再出现贴着触发按钮定位的浮层，也不再通过“助手模型 / 技术工艺模型”页签让用户分别保存。

## 2. 唯一事实源

- 唯一持久化文件是仓库根目录运行数据中的 `cpq_settings.json`。不得再把模型、参数或 Key 写入 `tech_app/tech_data/llm_settings.json`、`tech_settings.json`、`xbom_settings.json`、`rule_settings.json` 等第二份文件。
- 唯一对外读写接口沿用报价侧 `/api/settings`。技术工艺前端不得再读写 `/api/llm/settings`。
- 报价侧保存后，报价、配置、规则、技术工艺的新请求和已经存在的会话都必须读取到同一份最新配置；不得要求用户在技术工艺再保存一次，也不得仅在子进程启动时复制一次配置。
- 技术工艺调用模型时直接使用报价配置返回的当前 `model`、对应 provider、base URL、temperature、max tokens、thinking 及该 provider 的全局 Key。不得静默改用技术工艺默认模型或旧模型池。
- 如果报价当前模型不满足某项技术能力（例如所选模型不支持图像），调用必须明确报出当前模型与能力不匹配，不得另设“多模态模型”规避统一，也不得静默降级。

## 3. API Key

- Key 按 provider 全局保存于报价的 `cpq_settings.json.api_keys`；同一 provider 在四个助手和技术工艺中始终使用同一个值。
- 设置接口绝不返回 Key 明文，只返回 `configured`/打码提示等非敏感状态；日志、异常、审计记录和页面 DOM 不得包含已保存的明文。
- 输入框留空表示不修改；保存成功立即清空输入框。切换模型后，界面展示当前 provider 的 Key 配置状态。
- 不迁移、删除或覆盖用户已有 Key。首次兼容迁移如发现技术工艺旧 Key，只能在报价侧对应 provider 尚无 Key 时补入；冲突时以报价侧为准，并且不得打印两个值。

## 4. 居中弹出卡片

- 报价、配置、规则、技术工艺的侧栏“设置”和页头模型名称调用同一个设置打开器和同一套表单语义。
- 卡片使用全屏遮罩，视口水平、垂直居中；点击遮罩和按 Escape 可关闭，点击卡片内部不关闭。
- 卡片具备 `role="dialog"`、可访问名称、显式关闭按钮和键盘可见焦点；打开后焦点进入卡片，关闭后焦点回到原触发按钮。
- 卡片只显示一套字段：模型、Temperature、最大输出 Tokens、深度思考、当前 provider 的 API Key。删除“助手模型 / 技术工艺模型”双页签及技术工艺专属模型、Key 表单。
- 保存成功后所有已打开页面的页头模型名称刷新为同一模型；刷新页面后仍一致。

## 5. 兼容与禁止事项

- 不改报价流程、技术工艺五大流程、会话、任务、历史数据、角色权限和业务接口。
- 不删除历史设置或业务数据，不把真实 Key 写进测试、源码、fixture 或 changelog。
- 不修改 `open-claude` 包内文件，不通过硬编码 Key、固定模型或重启服务来伪造“全局生效”。
- 允许保留 `/api/llm/settings` 的短期兼容路由，但它只能在服务端委托唯一配置服务，前端和业务调用不得继续依赖它，且不得持久化第二份状态。

## 6. 验收场景

1. 从报价设置选择模型并保存，在不重启服务的情况下打开技术工艺，页头和实际请求均使用该模型。
2. 在任意入口更新某 provider 的 Key，报价、配置、规则和技术工艺随后的请求均使用这一个 Key；任意 GET 响应和日志均无明文。
3. 各入口点击设置或模型名称，均出现视口正中央的同款卡片；不存在锚点定位小浮层或双页签。
4. 两个浏览器页面同时打开时，一处保存后另一处再次打开设置即可读取最新值，旧会话下一次请求也使用新值。
5. 当前模型能力不足时明确失败，不静默切换模型。
