# 技术工艺与成本测算统一双栏工作台 Spec

状态：TDD Red，等待 DeepSeek 实现。

## 背景

报价助手已经形成“左侧持续会话、右侧业务工作台”的交互模式。技术工艺当前由多个独立页面组成：需求创建/确认/审核、图纸解析、工艺整合、成本测算、汇总审核与发布之间会整页跳转；其中部分页面自带会话，部分页面没有会话，布局和上下文不统一。

本需求只重组前端工作台与导航，不改变现有技术工艺、成本计算、审批、权限、存储及回传报价的业务语义。

## 目标

新增统一入口 `tech-workbench.html`：

- 左侧是项目级技术工艺 Agent 会话，步骤切换时不得销毁、刷新或重新创建会话。
- 右侧是工作台，承载技术工艺和成本测算全部步骤。
- 顶部展示三阶段步骤条，底部提供上一步、下一步及当前步骤主操作。
- 页面刷新后根据 URL 中的 `project`、`stage`、`task_id` 恢复同一项目和步骤。
- 从报价首页、待办卡片、历史任务和旧步骤 URL 进入时，都汇聚到统一入口。

## 信息架构

三阶段及稳定 stage 标识如下：

1. 接受工艺评估需求
   - `requirement-create`：1.1 创建
   - `requirement-confirm`：1.2 确认
   - `requirement-review`：1.3 审核
2. 解析技术工艺过程
   - `drawing`：2.1 图纸解析
   - `process`：2.2 工艺方案/组装整合
   - `cost`：2.3 成本测算
3. 输出工艺评估结果
   - `summary`：3.1 汇总结果
   - `report-review`：3.2 结果审核
   - `report-publish`：3.3 发布并回传报价

不得把成本测算拆到统一工作台之外。角色权限维持现状：工艺经理提交工艺、财务角色负责成本数字，审核和发布继续使用已有后端门禁。

## 推荐实现方式

采用渐进式同源容器，不重写后端和各步骤业务逻辑：

1. 新增 `tech_app/frontend/tech-workbench.html`、`tech-workbench.css`、`tech-workbench.js`，形成唯一页面壳。
2. 左侧复用现有 `agent-chat.js` 能力，但会话宿主只存在于统一壳中。
3. 右侧使用同源 iframe 或等价的受控 outlet 加载现有步骤页面，统一追加 `embed=1`。
4. 各旧步骤页面识别 `embed=1` 后隐藏自己的全局导航、重复会话栏、顶部壳和固定页脚，只保留业务内容；原 DOM id、API 调用和表单行为不得破坏。
5. 子页面通过 `postMessage`（固定事件名 `cpq:tech-workbench:navigate`）请求步骤切换；统一壳校验 `event.origin === location.origin` 和 stage 白名单后更新 URL/outlet。不得接受任意 URL。
6. 旧页面直达 URL 保持兼容：无 `embed=1` 时重定向到统一入口并保留 `project`、`task_id` 和对应 stage；不得造成重定向循环。

## 数据与状态契约

- URL 是可恢复导航状态的事实源：`tech-workbench.html?project=<id>&stage=<stage>&task_id=<optional>`。
- `project` 必填；缺失时返回技术工艺首页或展示明确的项目选择/错误态，禁止创建匿名项目。
- 左侧会话始终绑定 `project`，不能因 stage 改变生成新的会话标识。
- `task_id`、CPQ `session_id`、技术项目 `project_id` 的现有关联继续由既有桥接接口维护；前端不得伪造新的映射。
- 步骤完成状态必须来自已有 API/项目数据，不以浏览器本地点击结果冒充完成。
- 刷新、前进、后退必须恢复正确 stage；浏览器历史切换不得重复提交表单或任务。

## 入口与兼容范围

- `报价首页.html` 中技术工艺入口由 `requirement-create.html` 改为 `tech-workbench.html`。
- 技术待办的新增工艺、成本测算、成本复核入口统一携带 `project`/`task_id` 并进入对应 stage。
- 下列现有业务视图必须能在右侧工作台运行：需求创建、需求确认、需求审核、图纸解析、工艺整合、成本测算、汇总、报告审核、报告发布。
- 旧书签和历史消息中的页面链接仍可使用，并最终进入统一工作台。

## 视觉与交互

- 桌面端与报价助手一致：左侧会话建议 36%–42%，右侧工作台占剩余宽度；两栏各自滚动。
- 左侧输入区固定在会话底部，右侧步骤切换不改变滚动位置和草稿。
- 右侧不能出现第二个会话框、第二套平台导航或相互覆盖的固定页脚。
- 小屏幕小于 900px 时允许上下堆叠，但会话与工作台都必须可访问，不得隐藏关键操作。
- 加载、无权限、步骤不可达、子页面异常需在右侧显示明确状态；不能让整个会话区白屏。

## 安全与非目标

- 不改变后端 API 路径、数据库 schema、角色授权、成本公式、审批门禁或回传报价逻辑。
- 不删除历史会话、项目、任务、附件或本地/服务器数据。
- 不复制一套新的步骤业务实现；以现有页面和 API 为事实源。
- 不在本需求中创建 tag、Release 或部署。
- `postMessage` 必须校验同源及 stage 白名单；iframe/outlet 禁止加载外域 URL。

## 验收标准

1. 从报价首页进入技术工艺后展示统一双栏页面。
2. 九个 stage 均能在右侧打开，左侧始终只有一个项目会话实例。
3. 从 1.1 连续走到 3.3，切换步骤时左侧历史、输入草稿和项目身份不丢失。
4. 成本测算和成本复核均在右侧工作台完成，不再整页离开会话。
5. URL 刷新及浏览器前进/后退能恢复步骤。
6. 旧步骤链接能兼容跳转到统一入口，参数不丢失且无循环。
7. 未知 stage、跨域消息和任意外部 outlet URL 被拒绝。
8. 原有图纸上传、3D 视图、工艺确认、成本计算、审核、发布及回传报价回归正常。
9. 桌面和小屏幕布局无双导航、双会话或固定操作栏遮挡。
10. 新增静态契约红测转绿，既有相关测试保持通过。
